# GitHub AI 项目短视频 Workflow：策划与审片版计划 v7

更新：2026-10-25（America/Los_Angeles）
状态：试点已按最新指令切回 REA（morluto/rea）；参考片更新为新小红书视频（主要）及 Instagram Reel（辅助）。两条新参考的镜头、声音与节奏均待实际读取分析；具体 Brief、脚本分镜和生产尚未批准。

## 1. 本轮调整与第一版目标

本版按用户要求调整为“像拍电影一样，先把细节说明白，确认后再制作”。

- 输入以 GitHub 仓库 URL 为起点；使用场景与视频风格不再要求用户一开始就定义完整。
- Agent 对缺失的关键指导主动提问，并将回答整理成视频 Brief。
- 用户先看到创意、完整脚本、逐镜头分镜及制作执行计划；分镜和样式确认后，仅在获批范围内制作预演；预演确认并明确批准后，才能开始完整制作。
- 首条试点改回用户指定的 REA：https://github.com/morluto/rea。Jev 及重复扣款／工单分类示例退出当前试点；LivePortrait、rembg、TRELLIS 仅保留为后续备选。
- 当前主要参考为新小红书视频，辅助参考为 Instagram Reel；准确链接与读取状态见第 5F 节。新参考优先于此前的 xhslink 短链接，不能把旧片观察套用到新片。
- 交付面向抖音、小红书、YouTube Shorts：优先移动端竖屏、结果先展示、可静音理解。
- README 首屏展示、推广渠道和商业获客不在本版实施范围。
- 每个选题必须讲清“项目有什么用”，并用一个具体场景说明谁在什么情况下输入什么、得到什么、价值在哪里。
- 制作依据包含文字、标注视觉参考、样式帧、结构化分镜、适用的实际音轨和渲染反馈；代码或结构校验通过不能代替成片质量验收。

首版目标：做出一个可复用的 Skill，让 Agent 从 GitHub 仓库、用户指导与参考片出发，在创意获批后，产出类似参考片的完整动态项目介绍短视频。首条建议 30–60 秒、竖屏，具备统一美术、分场景图形设计、动效、配音与字幕；保留策划、批准记录、素材、来源与成本。具体时长、语言、风格均由用户确认。用户现在只要求更新计划，因此本轮不会启动视频制作。

## 2. 当前试点：REA，以及后续备选

以下能力和运行条件来自官方仓库资料；本轮未完整安装、推理或测试这些项目。视觉吸引力与试点优先级是策划判断，不是播放量预测。实际执行前需锁定版本、确认权重可用性和运行环境。

| 候选 | 可展示的结果 | 可做的视频切入点 | 实施难点 | 试点建议 |
| --- | --- | --- | --- | --- |
| [REA](https://github.com/morluto/rea) | Agent 通过分析工具获取软件结构和行为证据，辅助理解一个功能 | “复制富文本时，内容怎样从界面走到系统剪贴板？”——以注明来源的官方 Electron 案例解释实现链路 | 需区分原生分析、JavaScript/Electron 分析及各自依赖；案例与当前运行能力执行前再核对 | **当前试点**：先提案用途与一个案例，完整制作前审阅；本轮不安装运行 |
| [LivePortrait](https://github.com/KlingAIResearch/LivePortrait) | 静态人像结合驱动动作生成动态表情；官方提供推理、Gradio 和在线 Demo 入口 | “这张照片，能跟着动作动起来”——原图、驱动片段、输出同屏对比 | 需准备肖像与驱动素材、模型权重和合适环境；Apple Silicon 人像模式与 NVIDIA 环境能力、速度不同；动物模式限制更多 | **创意首选**：优先人像模式，先核实运行条件，使用自有或明确许可的素材 |
| [rembg](https://github.com/danielgatis/rembg) | 自动去背景，输出透明图；可通过 CLI、Python 和服务接口运行，支持 CPU 路径 | “杂乱背景里的主体，能抠得多干净？”——前后对照、局部边缘特写 | 视觉效果取决于素材和具体模型；头发、透明物体可能失败；代码许可不能代替权重许可核对 | **工程首选/备选**：输入输出清晰，便于先验证整条制作链路 |
| [TRELLIS](https://github.com/microsoft/TRELLIS) | 由图片生成 3D 资产，可展示旋转视频和导出物 | “一张图片，变成能转起来的 3D 物体” | 所核查原版 README 要求 Linux、NVIDIA GPU 至少 16GB 显存，并涉及 CUDA 依赖；部分子模块另有许可 | **后续挑战型试点**：在有合适算力并确认预算后选择 |

试点已按最新指令改回 REA，仓库为 morluto/rea。REA 是视频介绍对象，不替换制作 Skill 的宿主模型或 Remotion/FFmpeg 引擎；不默认将 REA 接入渲染、视频分析或评审。Jev 的 SDK、API 和工单分类不再作为本项目当前执行路线。备选仓库不影响 REA 已选定的状态。

LivePortrait 的旧地址 KwaiVGI/LivePortrait 本次查询跳转至 KlingAIResearch/LivePortrait；README 内仍有其他组织名链接。运行时以最终解析的仓库、commit、权重来源为准，避免跟错版本。

候选的最小核查项：结果是否一眼可见、一个短场景能否讲清、输入是否可获得、环境是否可支持、权重和样例能否使用。当前只核查文档，官方样例标记为参考，不直接当作我们生成的素材。

## 3. 输入：从仓库 URL 到明确的 Brief

当前已知指导：试点为 REA；参考是第 5F 节所列新小红书视频与 Instagram Reel。两条参考尚未实际读取，不能预设它们都是此前观察过的深色科技图形风格。Agent 应先分别拆解可访问内容，明确拟借鉴特征与差异，再提出统一视觉方向；只询问受众、平台、时长、声音等仍缺的关键指导。

### 必填起点

- GitHub 仓库 URL，或用户要求先推荐候选仓库。
- 有明确版本时记录 ref；没有时 Agent 提出建议并锁定版本。
- 用户已有的风格、素材、平台、语言、受众等指导全部复用，不重复提问。

### 缺失指导时，Agent 主动澄清

每轮优先问 2–3 个最影响结果的问题，提供简短选项和建议；有必要时再补问。第一轮先解决方向，第二轮再解决执行细节，避免一次性抛出大量问题。

| 维度 | 需要确认的内容 | 可给用户的选项示例 |
| --- | --- | --- |
| 受众与目标 | 给谁看，看完希望做什么 | 普通 AI 爱好者 / 开发者；觉得有趣 / 学会使用 / 进入仓库 |
| 主平台与语言 | 哪个平台优先，是否共用语音 | 抖音 / 小红书 / YouTube Shorts；中文 / 英文；其他平台派生版 |
| 叙事风格 | 语气、节奏、信息密度 | 有趣实测 / 实用教程 / 干净科技展示；可上传喜欢的参考 |
| 时长 | 内容取舍与节奏 | 30 秒 / 45 秒 / 60 秒；由 Agent 提案 |
| 呈现与声音 | 是否露脸，谁来讲 | 不露脸＋AI 配音 / 真人录音 / 无配音字幕版；音色和情绪 |
| 内容类型与主线 | 这条视频讲什么，哪些结论需实测 | 图形讲解型介绍 / 真实操作演示 / 二者结合；一个核心价值 |
| 素材与环境 | 输入从哪里来，在哪里运行 | 自有素材 / 合适的公开样例；本地 / 官方 Demo / 指定云环境 |
| 制作边界 | 算力、付费调用、尝试次数和完成标准 | 用户给出费用上限或先只做免费方案；批准可包含的小改范围 |

指导不完整时，Agent 可以提出“建议值”，但必须标明“待确认”。没有答复、等待超时、用户查看了文档，都不代表批准；不得用默认值直接进入视频生产。用户明确选择“按这套建议开始”时，才把对应选项记为确认。

Brief 最终应能回答：给谁看、项目有什么用、采用哪个具体使用例子、讲哪个结果、什么风格、哪个主平台、多长、哪种语言和声音、素材来自哪里、用什么环境、允许多少成本。Agent 先从仓库研究提出用途与例子；只有用户选择会影响方向或资料不足时再澄清，不让用户承担功能研究。

## 4. 用户会依次看到什么，以及在哪里确认

所有阶段都展示清楚当前进度、已确定事项、待定事项和下一步。**策划节点的确认要求来自用户本次明确要求。**

| 节点 | Agent 展示给用户的内容 | 用户的决定 | 通过后允许做什么 |
| --- | --- | --- | --- |
| G1：Brief 与方向 | 仓库摘要、项目用途、具体使用例子、关键问答、建议参数和待定项 | 选仓库，确认目标、风格和边界 | 做完整创意策划 |
| G2：创意、脚本与试读方案 | 两个创意、选定方向的完整旁白、字幕、用途与例子的对应关系、专名读法、时长估算；试读方法与成本 | 确认脚本；确认试读方式或用户自行试读 | 按已批方法试读计时，细化分镜；不生成完整动画 |
| G3：分镜、样式与预演授权 | 逐镜头表、全片粗分镜总览、三个代表性样式帧、标注参考板及拟采用的视觉规范、素材/声音方案、试读结果；预演范围、次数和费用上限；完整制作估算 | 确认内容和视觉，明确批准低成本预演 | 制作完整粗分镜 Animatic；首条或换风格时制作一个约 5–8 秒代表镜头试片 |
| G4：预演审阅与完整制作授权 | 可播放 Animatic、代表镜头试片（如适用）、节奏/可读性问题及修订；更新后的完整制作包与成本 | 确认叙事、节奏、动效质感，明确“开始完整制作” | 制作正式旁白、素材、完整动画及粗剪 |
| G5：粗剪审片与时序锁定 | 粗剪、统一时间码、问题清单和修改结果 | 确认镜头内容、顺序、长度和旁白同步 | 冻结时序，进行最终声音、字幕与画面精修 |
| G6：最终验收 | 精修成片、手机与平台预览、技术检查及交付清单 | 确认定稿 | 导出并交付最终发布包 |

审批针对可审阅的包，不要求每个内部动作单独确认。用户可以明确合并 G2/G3 审阅；已有充分指导时不重复问。首条或新风格默认保留 G3→G4 的预演验证；后续复用已批准模板时，可按用户明确授权的范围简化动效试片和审阅。范围内的工具调用、错别字和同步修复不重复请求批准。

“这个计划不错”是计划认可，不代表任何视频已经获准生产。每次批准要明确对应版本、允许的动作、费用与尝试上限。**G3 批准只允许预演；G4 批准才允许完整制作。** 本轮“补进计划”不构成试读、预演或正式制作授权。

### 试读、预演与完整制作的行动边界

- 可以先做：公开仓库研究、来源核查、写脚本/分镜、静态布局设计和预算。用户已有音轨可用于时长分析；静态设计不能伪装成项目实测结果。
- 脚本计时必须区分估算和实测：G2 展示试读方法；获批后可用用户真人试读、已有合适语音，或指定低成本临时 TTS 试读。产生外部费用时先写清上限；未获授权只能保留估算，不声称已计时。
- G3 之前不制作动态预演或动效试片。G3 之后，只执行批准的预演分辨率、声音方法、单镜头时长、修改轮次和预算；明确标记“预演/临时声音/占位素材”。
- G4 之前不下载大模型与部署正式推理环境、不正式推理录制、不制作完整精细动画或最终声音；正式 TTS 在 G4 授权后按批准的音色生成。
- 项目可行性确需提前试验时，单独展示目的、输入、运行影响、费用与输出，获得限定授权再执行。试验或预演授权均不自动扩大为完整制作。
- 预演素材可在授权和来源允许时复用，避免重复收费；各阶段记录实际费用与人工时间。
- 运行结果、声音时长或可读性不支持脚本时，显示差异并修订受影响内容；不靠加速旁白、缩小文字或伪造效果强行塞入。
- 画面时序锁定后仍可改动，但先说明哪些声音、字幕和动画需重新对齐，以及预算是否改变；只重新审阅受影响部分。

## 5. 拍摄前交付完整的“制作包”

用户需要能像审一部短片一样，明确看见视频将怎样展开。

### A. 创意提案

每个候选方向给出：
- 一句话概念、目标观众、一个核心看点；看点必须说明项目用途，并包含一个具体使用例子。
- 前 1–3 秒的画面与开场文案。
- 建议叙事结构：看点/结果 → 谁遇到什么问题 → 项目怎样帮助 → 具体例子的输入与输出 → 价值与限制 → 行动引导。创意可调整顺序，但不能省略用途与例子。
- 为什么这个切入适合当前项目；大致时长与素材需求。
- 与用户参考片的相似点、要避免的部分。

只做两个有差异的提案即可，避免堆砌几十个标题。确认一个方向后才继续细化。

### A1. 观众看点：用途与例子卡（必填）

每个选题先完成以下内容，再写完整脚本。不能只用“很火、很强、开源神器”代替实际价值。

| 字段 | 要回答什么 | rembg 的策划示例（未执行） |
| --- | --- | --- |
| 项目用途 | 项目能解决什么问题 | 去掉图片背景并保留主体 |
| 使用者 | 谁会需要 | 需要处理商品图片的小卖家 |
| 具体场景 | 在什么情况下使用 | 在家拍的商品图背景杂乱，想放到白底上 |
| 输入与输出 | 给它什么，得到什么 | 商品照片 → 去背景的透明图 → 编辑性合成的白底展示 |
| 观众价值 | 为什么值得关注 | 把处理商品图作为一种用途；质量和批量效率需实际验证 |
| 来源与限制 | 哪些已核实，哪些是预期 | 功能来自仓库；使用场景是策划举例，图片、边缘质量与耗时均未实测 |

一个例子贯穿脚本和画面即可，不必堆叠多个受众。优先使用可展示的前后变化、具体任务或清楚的流程。图形介绍也必须有例子：可以引用注明出处的官方案例，或用明确标记的解释性图示；不能把想象中的成功结果写成实测。

例子要进入成片主线，而非只存在于策划文档。G2 检查脚本哪几句交代用途和场景；G3 检查哪些镜头展示输入、结果与价值。示例不可用时先换例子或修订脚本，不能仅保留泛泛宣传语。

### B. 完整脚本、试读与计时

每个段落说明观众此刻要理解什么、为什么需要这个镜头，避免按 README 功能列表逐项念。展示完整旁白、屏幕上的文字、关键技术词读法、结尾行动引导。功能、速度、免费与否等说法区分文档依据和实测状态；未验证的结论不能写成既成事实。真实推理速度尚未测量时，不写“1 秒完成”等数字。

先给出粗略时长，再按 G2 批准的方法自然试读，记录总时长、分句起止、停顿、绕口词和未理解点。以可听懂的速度为准，不把字数公式当作实际语音长度。试读过长时先删减或重写信息，重大内容变化回到 G2 确认。G3 的分镜使用试读结果安排停留和换镜；正式旁白产生后再次校准，不能假设临时声音与正式声音长度完全一致。

### C. 逐镜头分镜

每个镜头至少包含：

| 字段 | 要说明什么 |
| --- | --- |
| 镜头编号与时间 | 起止秒数、预计持续时间 |
| 画面与动作 | 观众具体看到什么；图形解释、案例、命令、输入、操作或输出 |
| 理解目标 | 此刻要让观众理解哪一件事；对应哪条用途/例子或功能说法 |
| 注意力顺序 | 第一眼看哪里，随后出现什么；用大小、对比、位置、出现次序引导 |
| 动作与声音锚点 | 元素入场、强调、停留和退出分别对应哪句旁白/词语或时间段；无旁白时对应视觉节拍 |
| 来源与真实性 | 官方参考 / 待录真实界面 / 待生成真实结果 / 编辑性叠加；注明待验证项 |
| 构图与运动 | 全景、局部特写、前后对比；裁切、缩放、指针与转场 |
| 旁白与字幕 | 对应哪一句，屏幕重点写什么 |
| 声音 | 配音语气、音效、音乐起落 |
| 证据与验收 | 对应功能说法、预期结果、失败时怎样替换 |

文字分镜用于明确语义与约束，结合全片粗分镜总览判断信息顺序；不能仅凭文字认为视觉已经获批。需要真实静帧时可引用并标注官方示例，或经单独授权做小试验获取；完整制作素材在 G4 之后制作；G3 后仅做批准的预演素材。

### D. 样式帧、美术与声音说明

写清色彩、字体、字幕层级、封面风格、背景、转场强度、声音情绪、是否用音乐。给出可判断的具体描述，例如“浅底、单一强调色、大字字幕、以真实结果对比为主”，而不只写“高级感、电影感”。

### H. 动态预演与代表镜头试片

这两项属于限定范围的验证交付，在 G3 授权后制作，在 G4 一起审阅。

**Animatic：验证整条能否讲清。**使用粗分镜、占位画面、临时旁白及必要的基础切换，拼出与目标时长相符的完整低成本预览。临时旁白按 G2/G3 的批准范围执行。不追求最终画面精度，明确标注预演。检查开头是否迅速建立看点、信息顺序是否连贯、画面停留是否足够、字幕是否可读、声音与视觉是否争夺注意力。能看到全片节奏后，再决定是否删减内容或调整时长。

**代表镜头试片：验证最终动效质感。**首条视频或改用新风格时，挑一个约 5–8 秒的代表镜头，按接近最终质量完成标题/卡片的入场、停留、重点强调、退出及音画配合。优先选能代表整条设计难度的镜头，不只挑最简单的 Logo 动画。范围、尝试次数与费用在 G3 写清；它不是整条完整制作的授权。复用成熟且已获批的样式时可按明确授权省略。

无旁白路线不强制加入声音，预演改为验证字幕阅读时间与视觉节拍，并记录相应适用项。

G4 展示预演版本、待替换占位素材、时长、主要修改及完整制作预算。确认哪些动效会复用，哪些仍需制作。通过后冻结制作包；没有答复不自动进入完整制作。

### I. 粗剪、时序锁定与声音精修

正式旁白在精细动画前确定并检查发音、停顿和情绪，再按实际音轨校准镜头时长。若与预演差异明显，先展示影响，必要时重新确认节奏。音乐方向和声音提示可以前期设计；最终配乐剪接、音效位置、音量平衡与字幕同步在 G5 时序锁定后完成。

粗剪集中检查内容、顺序、节奏与同步；G5 通过后保存锁定版本、总帧数和镜头起止。之后的颜色、音量或不影响时长的修正可按已批范围处理。需要移动镜头、替换时长或改旁白时，重新校准受影响的字幕/音效/动画，并审阅相应变化；不把 Picture Lock 当成永远不可修改的硬禁令。

### J. 手机观看与最终验收

最终版本同时做技术检查和实际观看检查，发现问题后定位到时间码与镜头：
- 手机实际尺寸观看：文字和图示能否看清，重点是否明确，是否超出平台 UI 安全区。
- 静音观看：关键意思是否仍能理解；字幕与图形互补，不需要读满屏段落。
- 手机外放与耳机试听：人声是否清楚，音乐/音效是否盖住旁白，专名读音和字幕是否一致。
- 从头完整播放：开头、停顿、转场、结尾是否自然；没有黑帧、截断、缺字、占位素材或音轨缺失。
- 核对画幅、时长、帧率、编码、音轨与目标交付规格；不同平台派生版分别预览。

检查结果和人工反馈共用一个带时间码的修改清单，保留当前审阅版本，避免不同版本的意见混在一起。没有真实手机或试听条件时，将相关项目标为待用户设备复核，不能把模拟预览冒充实际设备验收；无声音路线的试听项记为不适用。第一版不加入演员选角、场地勘景或剧组通告等不适用的电影流程。



### K. 渲染、观察、修改：质量反馈闭环

在各阶段已有授权内执行“生成镜头 → 渲染 → 观察实际结果 → 定位问题 → 局部修改 → 再检查”。预演阶段只检查和改进预演及获批代表镜头；不以质量检查为理由提前生产整条精细动画。

1. **静态检查**：从实际渲染结果提取有代表性的画面和全片总览，对照获批样式与参考板。检查标题、布局、字体、溢出、遮挡、留白、前后镜头一致性；不能仅检查源码或编译结果。
2. **动态检查**：播放短片段，检查入场、重点强调、停留、退出及转场；至少覆盖关键变化前后，不能只挑稳定的漂亮帧。截图不能证明运动流畅或音画同步。
3. **全片检查**：完整播放，检查用途与具体例子是否讲清、注意力是否连贯、信息是否可读、声音是否同步。已有实际旁白时按音轨校准；无声路线按字幕阅读与视觉节拍检查。
4. **反馈落地**：每条问题绑定版本、镜头和时间码，写出观察到的问题、对应要求、修改动作与复查结果。例如“第 12 秒案例卡的说明文字在手机预览过小；减少文案并重新排版”，而非仅打“高级感 8 分”。
5. **控制返工**：G3/G4 预算包含检查、修改和复渲染，默认提议 1–2 轮而非无限循环；以用户批准的次数与费用为准。保存候选版本和差异，允许保留中间较好版本，不默认最后一次最好。

自动检查负责可验证问题，视觉评审关注层级、一致性、理解与动效。生成与评审采用分开的检查轮次和明确标准；第一版不依赖额外多 Agent 架构。需要额外模型服务时按已批工具与预算执行。Agent 自评只辅助修正，不能替代 G4/G5/G6 的用户确认，也不保证模型评分等于用户审美。

评价优先级：① 用途和例子讲清、事实准确；② 手机可读、无同步或遮挡错误；③ 视觉一致、注意力明确；④ 节奏和动效符合获批方向。美术优化不以牺牲前三项为代价，合格结果也不保证平台传播效果。

| 7–16s | 实际工具中载入输入，展示运行入口 | “用 LivePortrait，把动作迁移到照片上。” | 实际运行方式待确认；若走 CLI 就如实呈现 |
| 16–28s | 驱动动作与输出同步播放，局部放大变化 | “看表情和头部动作的变化。” | 对齐帧段；只指认确实发生的变化 |
| 28–35s | 原图/输出再次对照，呈现必要局限 | “这是这次输入下的结果。” | 若有明显瑕疵保留说明，不承诺所有照片都一样 |
| 35–40s | 项目名、仓库信息和简短 CTA | “项目叫 LivePortrait，源码在 GitHub。” | 确保手机上能读清；链接放平台文案 |

音乐与配音、封面、参考风格及预演预算在 G3 前确定；完整制作的运行方案与预算在 G4 前最终确认。该示例不会自动触发拍摄。

## 7. 适配抖音、小红书、YouTube Shorts

本节是首版创意与导出策略，不把经验性建议当成平台硬性规定，也不保证获得推荐。

### 通用母版

- 默认建议 9:16、1080×1920、30 fps、H.264/AAC；第一条建议 30–60 秒，最终由 Brief 决定。
- 开头直接给观众一个结果、问题或明显变化；不用长 Logo 片头。
- 一条只讲一个项目、一个清楚的主线。图形讲解以收益、机制和有来源的案例为主体；演示型以真实输入输出为主体，Brief 中确定内容路线。
- 支持静音理解：字幕与关键信息完整，但每屏控制信息量，避免长段文字。
- 镜头变化服务于理解；可以用前后对照、局部放大和关键步骤切换，不强制固定频率切镜头。
- 生成等待可压缩，明确标注“过程已加速/等待已省略”；成片长度不代表真实推理耗时。
- 保留干净画面母版、独立字幕和旁白，避免平台水印与平台音乐烙入所有版本。

### 三个平台的派生设计

| 平台 | 建议呈现方向 | 交付时要单独检查 |
| --- | --- | --- |
| 抖音 | 结果快速出现，口语开场，动作变化清楚 | 标题、封面、底部文案区及侧边按钮遮挡，字幕是否来得及阅读 |
| 小红书 | 具体使用场景、前后对照、可收藏的简短步骤 | 封面标题与裁切预览、正文中的使用条件、字幕与关键细节可读性 |
| YouTube Shorts | 减少铺垫，清楚展示核心价值或一次输入输出，以及项目身份 | 标题、字幕语言、移动端 UI 遮挡；需要英文旁白时单独确认并对齐 |

上述方向可由用户风格偏好覆盖。中文旁白可以用于 Shorts，不自动翻译或额外生成英文版。三平台优先共享核心素材，再派生开头、字幕位置、封面和文案；不默认拍摄三条独立视频。

安全区用可配置模板叠加检查，在送审包展示具体布局。平台 UI 与封面裁切会变化，发布前核对当前预览，不宣称一组固定像素可以永久通用。

YouTube 官方目前允许符合条件的方形/竖屏 Shorts 长至三分钟；本项目建议 30–60 秒是内容取舍，并非平台上限。抖音与小红书发布限制、声明选项等在实际发布时再按当前规则核对。

配乐选择可跨平台使用的自有或适当授权素材；平台曲库音乐不能默认跨平台复用。AI 内容标识根据素材性质与发布时平台要求核对，并保留项目演示来源与必要说明。

## 8. 实施流程与技术边界

### 策划与预演工作流

1. inspect：读取仓库、官方文档和运行要求，保存事实与来源；拆解参考片的可观察风格。
2. clarify：复用已有指导，只问关键缺口，生成 Brief；等待 G1。
3. use-case/pitch/script：完成用途与例子卡，提出两个创意；选定脚本必须交代用途并贯穿一个具体例子，准备试读方法与时长估算；等待 G2。
4. readthrough/storyboard：按批准方法试读计时；制作标注参考板、逐镜分镜、全片粗分镜总览、三个样式帧及共享设计规范；明确理解目标、注意力顺序和声音/动作锚点，展示分阶段预算及检查修改次数，等待 G3。
5. previsualize：按批准范围制作 Animatic；首条或新风格制作约 5–8 秒代表镜头试片；通过实际渲染与播放检查节奏、注意力和动效；局部修改并展示差异，等待 G4。
6. approve-production：冻结获批脚本、分镜、预演、声音、执行方法与预算版本，才进入完整制作。

预期产物：project.json、facts.json、reference-profile.json、annotated-reference-board、brief.json、use-case.json、concepts.md、script.md、readthrough.json、storyboard.json、style-frames、storyboard-contact-sheet、design-tokens.json、preview-plan.json、animatic.mp4、motion-test.mp4（如适用）、production-plan.md、approvals.json。MP4 预演只在限定授权后产生；批准前的计划中仅记录预期路径。

### 完整制作与后期工作流（G4 之后）

1. prepare：按获批方案准备素材、环境和可选实测；图形讲解不强制安装项目或下载权重。
2. narrate：生成正式旁白，检查读音、停顿和实际时长，校准预演时间轴；显著变化先回报。
3. assets/capture：准备图形场景、来源媒体；如有获批实测，执行并保存输入、参数、原始输出和录像。
4. animate/rough-cut：按实际声音和时间轴完成动画与粗剪；可先放临时音乐与音效。复用获批布局与视觉规范，按 K 节渲染检查、局部修复并复渲染，在已批轮次和预算内执行。
5. review/lock：提供带时间码粗剪，按集中反馈修改；等待 G5 确认内容、顺序与时长，记录 picture-lock.json。
6. finish：完成最终音乐/音效剪接、混音、字幕同步、画面精修与平台适配。
7. qa/final-review：运行技术检查，完成手机、静音、外放/耳机观看，展示最终版本及问题修复；等待 G6。
8. package：导出母版、平台派生版、封面、字幕、文案与来源记录，保存费用和版本、渲染检查记录与问题修改清单。

Agent 持续展示阶段、成果、费用和阻塞；阶段授权范围内的动作不重复确认。预演与成片分开标识并记录，避免把预演通过误记为最终定稿。

### Skill 的交付与调用方式

首版交付一个可在 Agent 中调用的 Skill：入口说明、提问策略、仓库研究规则、参考片风格说明、创意/脚本/分镜模板、生产批准规则、渲染脚本和验收清单。TypeScript CLI 是 Skill 调用的执行器，不是唯一面向用户的入口。

建议调用输入：仓库 URL＋可选 guidance＋可选参考视频。输出：先生成策划审阅包；先经限定授权生成预演，完整制作获批后生成粗剪，最终确认后交付成片 MP4、封面、字幕及来源记录。已有指导跨阶段保留。

### 技术起点

- 一个 TypeScript CLI 控制任务状态；JSON Schema/Zod 校验结构化输入。分镜是语义和执行约束，不是完整美术设计；结构合法与代码能编译都不能视为成片合格。
- 一个项目适配器负责运行与素材捕获。Web 项目可用 Playwright；CLI 项目可参考 VHS；AI 推理项目使用该仓库支持的 Python/CLI 接口。不要把所有项目强行包成浏览器操作。
- 拟采用代码化图形介绍时优先评估 Remotion（具体风格待新参考分析与审阅）：项目标题、功能卡片、证据卡、命令窗口、仓库收尾五类场景，参数驱动并固定时间轴；FFmpeg 负责音视频处理与编码。偏实录的简版可只用 FFmpeg。先确认技术路线与锁定版本许可，再实施；不能声称参考片作者使用了这些工具。
- 文本/视觉能力用于研究、创意与实际渲染结果评审；TTS 采用一家服务并保留真人录音接口。检查接口分别支持静态帧、短片段与完整音视频；不支持的检查明确记为待人工复核，不用截图代替声音检查。
- 单机、单任务、逐阶段产物；先不增加用户账号系统、队列集群或自动上传。

## 9. 状态、批准与修改

计划状态包括：INSPECTING、NEEDS_BRIEF、BRIEF_REVIEW、SCRIPT_REVIEW、READTHROUGH、STORYBOARD_REVIEW、AWAITING_PREVIEW_APPROVAL、PREVISUALIZING、PREVIEW_REVIEW、AWAITING_PRODUCTION_APPROVAL、READY_FOR_PRODUCTION、PRODUCING、ROUGH_CUT_REVIEW、PICTURE_LOCKED、FINISHING、QA、FINAL_REVIEW、DELIVERED；失败进入 BLOCKED 并给出具体原因。READTHROUGH、PREVISUALIZING、PRODUCING 分别校验对应授权；不能只改状态绕过批准。

每条批准记录绑定：批准类型（试读/预演/完整制作/时序锁定/定稿）、仓库与来源版本、Brief/脚本/分镜/样式/预演版本、声音与运行方法、阶段预算和尝试上限、可包含的修改范围、用户明确的批准记录与时间。

约束：
- 生产阶段命令先验证批准对象与当前输入一致；仅创建文件或切换状态不能伪造用户批准。
- 选题、核心脚本、关键镜头、音色、外部素材来源、运行路径或费用上限发生实质改变时，重新提交受影响部分。
- 错别字、字幕错位、编码错误等在已批范围内修复，无需重新确认全部创意。
- 用户只说“继续完善计划”时保持策划状态；没有答复不跨越批准节点。
- 阶段输入发生变化时，使相关下游产物失效；从对应阶段恢复，保留此前版本。
- 费用上限到达、结果不支持脚本、资源不可用时暂停相关生产，给出可审阅的替代方案。
- 初期不承诺逐比特相同；保存足够信息解释和尽可能复现实际生成过程，并如实记录模型的随机性。

## 10. 验收标准

### 策划完成

- 缺失指导已提问；已有指导完整保留。
- 项目、受众、目标、用途与具体例子、主平台、时长、语言、风格、声音、素材、运行条件和预算均确认。
- 用途与例子不是仅写在策划中：脚本和分镜标明对应句子与镜头，能解释谁在什么情况下输入什么、得到什么、有什么价值；策划示例、官方案例和本次实测明确区分。
- 完整脚本、试读结果与每个镜头向用户可见，样式帧、素材类型、待验证部分及执行方法明确。预演和动效试片已按批准范围完成并审阅；首条不跳过全片节奏验证。
- 用户明确批准 G4 对应完整制作包；仅批准计划、试读或预演时不能进入完整制作。

### 成片完成

参考片对齐检查：必须是完整动态短片，不能只交脚本、PPT 或静态画面拼接样例。统一背景、字重、强调色和卡片规范；有清楚的场景推进与受控动效；字幕、旁白和视觉重点对齐；关键图文在手机实际尺寸下能读清。G3 展示首屏、能力场景和案例场景的静态设计及动作说明；G4 通过预演确认全片节奏、通过试片确认代表动效；G5 锁定时序；G6 复核最终声音、视觉和手机观看体验。样式相似不等于复制原视频文案、账号形象或未经许可的媒体。

- 图形讲解的关键功能说法有可追溯来源，官方案例与本次实测明确区分；凡声称本次实测的镜头，都有真实运行证据。
- 与获批 Brief、脚本、分镜、样式帧和共享视觉规范一致；变更已按范围确认。
- 有实际渲染帧、动态片段和全片播放的检查记录；问题绑定镜头/时间码，并完成范围内复查。代码能编译或模型自评高分不能代替此项。
- 关键效果在手机画面可见，静音时能理解；旁白和字幕同步、专名读音正确。
- 编码、画幅、时长、音轨符合所选交付规格；平台 UI 叠加预览无关键遮挡。
- 保留输入、原始输出、运行参数、剪辑清单、素材来源与费用记录。
- 用户完成粗剪审阅、G5 时序锁定及 G6 最终确认；声音精修和手机验收记录完整，交付后才标为 DELIVERED。

初期不将爆款、播放量或收入列为制作验收承诺。重点测量每阶段机器耗时、人工分钟数、推理尝试次数、API/算力费用、审稿轮数以及返工原因。
