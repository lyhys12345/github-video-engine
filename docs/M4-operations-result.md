本轮推进原 M4 中可独立实施的诊断部分，未越过 M2 G4，也未开始完整 M3 制作。**M4 全部完成、正式费用账本、通用局部修正和最终交付仍未成立。**

## 实现

新增 `src/operations/audit.ts` 和公开 `audit --data <existing-directory> [--out <new-report.json>]`。报告版本 `operations-audit/1.0`，涵盖 SQLite 结构/版本/原始键、完整输入指纹、步骤与任务、来源/修订/制作包/审批关系、内容地址文件及嵌套 JSON 引用、跨环境尝试预算、已有租约观察和未记录费用。没有调用媒体工具或网络，没有恢复/取消/迁移/审批源状态。

历史包的 schemaVersion 未变却缺少新必需字段，是兼容性缺口；仅对“补回该单一字段后完全符合当前 schema、且未被选为当前包”的历史形态分类 legacy，不将任意坏对象宽松接受为旧版。当前选择不兼容则失败。

## 实际发现、失败与修复

1. 普通受限环境无法为测试 fixture 创建硬链接；使用已授权的本地执行权限运行实际存储测试。原失败保留，没有把受限运行称为通过。
2. `readOnly:true` SQLite 仍在源目录创建 WAL/SHM：无写入断言真实失败。修复为读取稳定 main＋WAL 到自有临时目录，复核源文件集合/哈希并只读打开副本；独立的活动 WAL 测试证明没有漏掉未 checkpoint 的提交。不会删除第一次原型已创建的源辅助文件以隐藏历史。
3. CLI 测试的 Windows `--import C:/…` 不是合法 ESM URL；改为 `pathToFileURL`，子进程专项复跑通过。该错误属于测试调用方式，不伪称产品功能已运行成功。
4. 类型检查发现可空索引/引用的窄化问题，修复后实跑通过；首次组合专项 7/13 通过、6 失败，原日志 `operations-tests-initial.log` 保留。最终结果有单独日志，未覆盖首次失败。
5. 两位独立 Judge 在候选 2 复现了 major：同一制作包的任务若记录不同 scopeKey，三次尝试会被拆成 2＋1 而误报未超两次限额。该轮 FAIL 和全部 187 个原文件保留。修复后批准范围从任务类型＋制作包哈希推导，不信任 scope 标签；不一致记录明确失败，聚合仍计为同一范围的 3/2。真实 SQLite 反例已加入回归，原合法范围和缺省 scope 的历史记录仍被正确识别。没有修改旧任务记录或生产批准。
6. 候选 3 证据 Judge 又复现了 M0 评价目标不一致：严格 schema 的评价可写 passed:true 却指向另一个视频哈希，审计原先未检查这个字段。该轮 FAIL 和全部 196 个原文件保留。修复后核对 M0 验证 spec、解析素材映射、评价→已提交视频哈希、评价必需检查以及发布清单→任务/环境/输入/各阶段输出；新增错误目标和“通过标志掩盖失败检查”两个模拟反例。没有用解码或感知质量替代元数据一致性，也没有修改原 M0 evaluator/renderer。

## 保存与仍未完成项

新增前已按原候选核查并保存 M2 的 136 个文件；旧源和旧报告对应原冻结版本，路径 `reviews/M2/round-1/frozen-before-M4-audit/`。M0 原视频仍为 `674b8011fc227b47c493f097fe424fc85c9f24e3dc091cb8db0a0ac3b187cc73`。新增模块/CLI 源码意味着新的执行环境版本，不能把旧预演结论迁移为新渲染的 PASS。

快照是分库一致读取，不是跨库与文件的原子备份；本轮不提供活动生产在线备份承诺。原 candidate 文件的格式字节不能由 receipt 中解析后的 JSON 重建；报告不会假称重新验证其原始字节哈希或重新作出 judge 决定。TaskRunner 未持久化历史缓存命中事件，过去每次尝试的完整耗时也未保留，对应数据保持未知/部分覆盖。

M0 的 EvaluationResult 明确携带目标视频 SHA，当前审计验证该关联。历史 M2 的 `production-ffprobe-v1` 评价只有检查/探测结果，没有目标哈希；审计仅核对其清单/输出引用和通过标志，并在报告中明确“无法从该 payload 独立证明评价对应确切视频字节”。不能凭空补写旧评价的来源绑定；完整 M4 需要新的制作评价收据设计。

正式费用账本、可靠的可重用修改/失效工作流、完整交付包与 M3/M4 全部验收仍需继续实现。M2 的真实听觉/连续审片缺口原样保留；本诊断功能不能替代它。
