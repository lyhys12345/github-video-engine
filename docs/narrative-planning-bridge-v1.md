# Complete narrative planning bridge

This additive workflow connects the existing read-only GitHub URL capture and Story planner to one complete, explicitly authored narrative parent. It does not rewrite Story or sequence, generate a whole video, extract frames or claim automatic repository understanding. Existing sequence assembly is a separate operation for ordered independent examples, not a guarantee of narrative continuity.

1. Run `explanation start --spec <pinned-url-request.json> --data <state> --out <new-capture>`.
2. Run `explanation narrative-packet --task <start-task> --data <state> --out <new-authoring-packet>`. Read the numbered source files, narrative schema and Story schema. A human or session agent must author the thesis, factual claims, complete narration/visuals, screen text, transitions, ending and estimated durations.
3. For supported source-grounded scenes, run `explanation narrative-story --task <start-task> --spec <authored-story.json> --data <state> --out <new-story-output>`. This reuses the existing `planCapturedStory` compiler, snapshots the captured source bytes and produces a normal repository-bound Story task. It does not render a scene.
4. Author the narrative JSON. It requires a first hook, mechanism and example scenes, a limitation scene, and one final closing scene. Each scene explicitly declares supported-story, needs-evidence or needs-adapter. Unsupported or unverified scenes stay in the full editable plan. The total estimated duration is at most300 seconds; timings are authored editorial intent, not measured audio.
5. Run `explanation narrative-plan --task <start-task> --spec <narrative.json> --data <state> --out <new-plan-output>`. Its bundle contains the complete editable narrative, linked Story snapshots, source workspace and numbered sources, scene dispositions, review packet and receipt schema.
6. Independently review every required packet item. Repeat narrative-plan with `--review <receipt.json>` to commit an attributed receipt as a separate candidate. narrative-status and narrative-export use the narrative task ID and committed source/child inputs; the original authored files may move.

A supported-story scene must match the complete repository/source fingerprint, expected Story graph hash, selected shot IDs, exact selected narration/visual text and all selected claims/citations. Its declared adapter is checked against the established HTTP, image-mask or scalar-rule Story vocabulary. This is a source-bound planning link, not new rendered-scene validation or automatic animation planning. The exported nested Story retains its own pending semantic/media review; the narrative receipt does not approve every nested actor/object/operation label, rendered pixel or sound. That requires the existing Story review and media workflows separately.

The required narrative review items include the entire brief/thesis and open questions, every scene title/role/duration, complete narration/visual text, all on-screen text, every transition (including the explicit final ending), and each execution disposition/mapping. Exact quotations establish provenance rather than entailment. A new thesis, screen assertion, transition, ending, timing or mapping invalidates an old receipt even when all source quotes are unchanged. Reviewer identity remains unauthenticated, semantic truth is not machine verified and approval remains none.

An unresolved receipt is preserved as review-unresolved; processing it is a successful planning operation, not factual acceptance. Even a fully supported written-plan receipt cannot turn needs-evidence or needs-adapter scenes into supported scenes. The status exposes both review and scene states independently. All final owner/G6 and audiovisual acceptance remain pending. No paid API, deployment, target-code execution or formal whole-film authorization is implied.
