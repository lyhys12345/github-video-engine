# Non-circular M3 review → engineering lock → delivery sequencing

Adopted acceptance sequencing, 2026-10-26. The original proposal is preserved in work/m4-final-scope. This document creates neither a review verdict nor a production receipt; actual reports, lock execution and postcondition checks remain required.

## Current mechanism read

`FinalizationStore.lock` reads actual full-render result and current conditional authority; it requires the exact M3 policy, G5 delegation, candidate.finalization binding to package/authorization/full-task/media/subtitles, and coverage of the actual output/owner hashes. It then requires all six reports to pass `checkGateV2`, checks unchanged raw review bytes, and creates a durable engineering-picture-lock receipt containing candidate/rules/delegation/report hashes and CAS copies. `export` later embeds this receipt and review bundle in a new immutable delivery identity. Tests explicitly label report fixtures MOCK and cover success, duplicate, stale/wrong/missing/weak policy/report denial and exact exported receipt bindings.

Therefore an actual G5 lock cannot honestly exist before the six real PASS reports. A reviewer demand for an already-issued actual lock as a prerequisite to those same PASS reports creates a dependency cycle. The M3-10 wording permits a bound engineering “picture-lock/final-review receipt”; this supports evaluating the real final-review binding first and completing lock/export postconditions afterward. This is sequencing, not waiving an unmet technical requirement.

## Proposed two phases

1. **Frozen actual media/final-review candidate A.** Freeze actual source, authority, complete final task and outputs, the pre-lock draft delivery, tests/raw evidence, owner record and policy. Add the exact `candidate.finalization` required by `FinalReviewBindingSchema`. Keep the actual candidate's final-review binding distinct from a successfully persisted G5 receipt. Raw tests of lock behavior remain clearly MOCK. Every active role independently reviews all applicable non-deferred criteria against A. For M3-10, explain that actual media, timing and final-review binding are present, the lock/export mechanism is verified by labeled tests, and actual primary lock issuance is the deterministic post-review postcondition. Do not state “actual G5 already issued.” If a judge interprets the contract to require issuance for its initial PASS, reconcile this sequencing explicitly with that judge; do not replace its UNVERIFIED vote with fabricated PASS.
2. **Run actual lock after real gate PASS.** Preserve A and its six report bytes. Execute the public `final lock` with those actual inputs. Record command/exit/task receipt and byte hashes. Repeating once can establish idempotence without rendering. Export to a new directory, retaining the pre-lock draft and all original media.
3. **Verify postconditions B and obtain affected-role acknowledgments.** Produce a small append-only postcondition manifest tied to candidate A and its exact reports. Verify receipt candidate/rules/delegation/six report hashes; all actual input/audio/video/subtitle/timeline/owner bindings; immutable retained reports; identical media hashes before/after; pending owner status and no historical G4/G6 fabrication; post-lock export's receipt/review bundle/files; public read-only audit and external delivery hashes; duplicate lock/export preserves the first records. Product, reliability, evidence and security should acknowledge these applicable postconditions. Video/content roles need recheck only if relevant media/copy/assets changed; normally hash identity is sufficient. These acknowledgments are separate records, not edits to the six report bytes already locked.
4. **Final engineering acceptance.** Only after B verifies and affected reviewers acknowledge may the root mark M3 engineering complete. M4's final candidate includes A, the issued receipt, actual delivery and B/acknowledgments, and all six M4 roles review that closure. Owner AV/G6 remains pending.

## Avoid an infinite hash chain

Do not rewrite candidate A or its reports to insert the receipt which hashes them. B references A and the issued receipt; it is not itself a prerequisite of A's lock. Do not repeatedly relock merely to include each acknowledgment in itself. Current `export` searches the first matching successful lock task for a fullTaskId; if multiple actual lock receipts are deliberately issued, explicitly verify which receipt the export selected and resolve any mismatch before acceptance. This is an observed implementation characteristic, not a demonstrated failure in the current one-lock flow.

If source or actual media changes during review/verification, this shortcut no longer applies: create a new source/media candidate, re-establish authority within retained budgets, and rerun affected roles. A postcondition exception must never be used to paper over a substantive implementation defect.
