# 启用矩阵（供用户 review）

每个 M 开始时，根据已批准范围确定启用角色和主责条款，并写进验收合同。新增本来会触发专项的工作，必须同步更新启用清单；不能在发现问题后把专项移出清单来获得通过。

| 情况 | 基础角色 | 必需专项 | 说明 |
| --- | --- | --- | --- |
| M0 固定合成工程示例 | J1、J2、J3 | 无默认新增 | 已有技术/内容完整性由基础角色覆盖；不要求电影级美术 |
| 真实 GitHub 项目研究或事实性脚本 | J1、J2、J3 | J5 | 核查实际研究/脚本产物，不要求此时完成成片 |
| 对齐已确认参考的预演/真实成片，或视听/字幕验收 | J1、J2、J3 | J4 | 按阶段批准的预演/正式质量标准判断 |
| 真实项目介绍成片，含事实说法 | J1、J2、J3 | J4、J5 | 既核对视听，也核对说法来源 |
| 执行真实仓库/不可信脚本或依赖，处理凭证/私人数据，外部写操作，新增远程资产入口，多用户或隔离机制 | J1、J2、J3 | J6 | 执行本身仍需在已有授权内，Judge 不能替用户授权；已批准可信固定工具链安装不单独触发 |
| 同时触发多项 | J1、J2、J3 | 对应专项全部启用 | 不是从专项里任选一个 |

“必需启用”是该方案拟采用的规则；新增专项配置尚待用户 review，本轮未运行它们。未触发的专项记为未启用，不填一份虚构 PASS 报告。

一旦启用，专项角色与基础角色具有相同的条款阻塞效力：FAIL/UNVERIFIED 都不能整体放行。未启用角色若收到可复核的范围内严重风险，先让主责角色复核；若实际范围已触发专项，则应纠正启用清单，不得忽略风险。

当前 v1 程序门禁仍固定三个基础角色。未来启用专项时，需要把 activeRoles/requiredCriteria/report 的完整性一并纳入对应阶段的实际门禁；不能使用 v1 的三角色 PASS 冒充全部活跃角色通过。本轮仅提供配置和规则，不声称已经完成这项接线。
