## Result and repair candidate

**Selected model reports match inspected actual-frame boundaries. Product integration risk: moderate; repair candidate.** Overall semantic, audiovisual and owner acceptance remain UNVERIFIED. The API explicitly records `declaredTemporalChecks` and documents the distinction, but a common shell or CI consumer can falsely treat an unmet check as passing if it inspects only process exit status or the top-level `state`.

Actual isolated `presentation timing-check` repeated the retained original rembg spec and exited 0, printed top-level `state: succeeded`, `integrity: verified`, and `declaredTemporalChecks: failed` plus a failed per-check verdict and zero overlap. Actual `timing-check-status` likewise exited 0 and displays the same top-level failed verdict. This is not omission of the verdict: a user reading the JSON and docs can see it. It is a concrete integration hazard for consumers treating exit 0 or `state: succeeded` as a content-quality gate. It is not evidence that any existing consumer actually made that mistake.

**Recommended product repair:** when invoking `timing-check` as a gate, return a distinct nonzero exit status for completed `declaredTemporalChecks: failed` while preserving its durable task ID/report and structured output. `timing-check-status` and `timing-check-export` should remain successful retrieval operations when the stored report is readable, while clearly retaining the check verdict; document both meanings and the unchecked/pending state. An explicit opt-in gate mode could preserve existing process-exit compatibility. Re-test a failing declaration, a passing declaration, an execution error, cached replay and status/export of the failed report so failure reporting is not mistaken for loss of its evidence.
