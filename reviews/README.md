# 三个 Judge 的里程碑验收制度

状态：按用户本聊天的授权建立；先在 M0 试审。Judge 的意见是可质疑、可校准的证据判断，不代表已经证明比原流程提升了多少质量。

## 角色与职责

| Judge | 主问题 | 必须直接查看的证据 |
| --- | --- | --- |
| product | 做的是用户要求的功能吗，用户能完成本阶段的实际任务吗？ | 本阶段合同、公开入口、实际输出、可观察行为 |
| reliability | 出错、中断、重复、取消、并发时，状态和产物是否仍可信？ | 核心代码、边界/故障试验、状态与资源清理 |
| evidence | “通过”的结论是否有足够、匹配该版本、可复现的证据？ | 原始测试、构建指纹、日志、产物、独立复核 |

角色说明见 roles/。每轮使用新上下文，先不读取实现者的总结性结论，也不读取其他 judge 的报告。三者可以使用同一套原始证据，但要独立作结论。同一模型的三个实例仍可能共享盲点；上下文隔离不等于统计独立，也不自动等于跨模型复核。

## 权限与用户的参与

用户将日常里程碑实现审阅交给三个 judge；实现者负责修复，judge 负责复验。用户主要审 judge 的标准、抽查与争议，以及最终里程碑的产品结果。

用户仍决定目标、范围、审美/质量样例和付费/发布等既有授权边界。Judge 不能通过放宽需求、豁免严重故障、重写测试或补一句“建议后续处理”来把失败变成通过。审阅授权不等于自动批准下一个尚未授权的 M；当前仅 M0。最终 M 仍须用户明确验收。

## 每个 M 的工作顺序

1. 实施前确定本 M 合同：目的、明确不做的事、编号的验收标准、关键场景、预算、授权边界、通过样例和失败样例。用户可以一次认可完整里程碑路线，之后不对已授权范围逐 M 重复请求确认；当前只有 M0 获批，不能从 M0 推测 M1 路线。
2. 提交候选版本，记录源码、测试、输入、必要产物的文件哈希；无 commit 时明确使用文件快照，不能编造 Git revision。
3. 三个 judge 对同一候选快照独立检查。测试与工作目录隔离；共享源码只读，禁止一边审阅一边改变候选。
4. 每份报告逐条列出 PASS / FAIL / UNVERIFIED / NOT_APPLICABLE，说明实际命令、证据、模拟范围、限制。未做就写未验证。
5. 实现者修复问题后建立新快照。发现问题的 judge 必须复验，其他 judge 根据影响补充回归；不能把旧版本的通过直接套到新版本上。
6. 三份报告齐全、候选版本匹配、必需标准都有证据、无未解决 blocker/major，才可记为技术通过。不能用平均分或 2/3 投票冲掉失败。
7. 对事实分歧先做区分性实验；有能力限制则保持 UNVERIFIED。目标/审美分歧或两轮修复后仍无法解决的争议，交用户审 judge。保留原始不同意见。

## 结论含义

- PASS：本角色覆盖的必需标准满足，无未解决严重问题；允许列明不影响本 M 的 minor。
- FAIL：至少一项本阶段必需标准有实证失败，或存在未解决 blocker/major。
- UNVERIFIED：缺必要证据、环境不能执行、候选变化或报告不完整；不能当作通过。
- NOT_APPLICABLE：只适用于某项标准，需由合同解释原因；不能把本阶段明定的必需项改成不适用。

严重度按影响而不是措辞：blocker = 安全/数据完整性/关键路径根本不可用；major = 本 M 必需行为或证据不达标；minor = 不影响合同兑现的改进。每个问题给出复现、预期/实际、文件位置或产物哈希，以及判定所依赖的合同条款。

## 如何 review 这三个 judge

先用 M0 校准：看它们能否找到可复现问题、是否误把 M1 功能当 M0 缺陷、是否明确区分原始证据与作者断言，以及是否承认没测到的内容。未来用少量已知正确/错误样例检验误放行和误阻塞，保留不会提前暴露给实现者的验收场景；不为了凑问题数量制造缺陷。

判断机制是否提高质量，要看：独立发现并确认的问题、漏掉的严重问题、误报、跨版本回归、修复后复验以及用户抽查的一致性。单次三人一致或测试数增加，都不能证明质量提升。

## 用户每次收到的摘要

一张三角色结果表；最严重的未解决问题；候选哈希和最关键产物；哪些是实际运行、哪些仅检查代码；需要用户决定的范围/审美争议。详细报告保留原文，不由实现者改写掉不同意见。

最小程序闸门：`node reviews/check-gate.mjs reviews/M0/round-1/candidate.json reviews/M0/gate.json`。退出码 0=PASS、1=FAIL、2=UNVERIFIED。它检查报告齐全、版本/文件哈希、必需条款、证据路径和严重问题，不验证模型意见的真实性，也不提供防管理员篡改的签名。自测用 `node --test reviews/check-gate.selftest.mjs`，与引擎测试数量分开记录。

## 依据与限制

采用程序化硬检查、明确 rubric 的模型审阅及用户校准的组合。参考 [Anthropic 的 agent evaluation 实践](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)：模型评分有不确定性，需和人的判断校准；可客观验证的结果应优先实测。这份资料不证明“本项目的三个 judge 一定优于一个”。本制度是针对本项目的工程选择，需通过实际漏报/误报记录验证。
